# 후보고: BOZOR 서비스 v1 개발

- 작성일: 2026-10-11
- 브랜치: `feature/v1-service` (아직 커밋하지 않음)
- 범위: 2차 회의에서 정한 **이번 학기 핵심 기능 전체**. 사진 → AI 초안 → 검수 → 발행, 상점·상품 조회·검색, 주문(결제·배송 제외), 목 로그인, 검증 지표.

## 1. 어떤 순서로 했나

**현지 조사 → ERD → API 명세 → 구현 → 검증** 순서로 진행했다.

- 조사를 먼저 한 이유: 통화(소모니), 흥정 관행, kg 판매, 언어(타직어·러시아어) 같은 사실이 **테이블 구조를 바꾸기 때문**이다. 구현 뒤에 알면 고치는 비용이 크다.
- ERD를 코드보다 먼저 한 이유: PoC의 테이블(`scan_records` 하나)은 서비스 구조와 완전히 달라서, PoC를 먼저 다듬으면 그 작업이 대부분 버려진다.
- 단계마다 **실제 DB와 브라우저로 검증**했다. 문서로만 맞다고 넘어가지 않았고, 그 과정에서 버그 8개를 찾았다.

## 2. 전체 구조

```
React(5173) ──/api──▶ Spring Boot(8080) ──▶ PostgreSQL
                          │   ▲
               스캔 워커 ──┘   └── 사진 파일(로컬 디스크, 나중에 S3)
                          │
                          └──▶ FastAPI(8000) ──▶ Gemini
```

- 브라우저는 FastAPI를 직접 부르지 않는다. **Gemini 키는 AI 서버에만** 있다.
- AI 분석은 Spring 안의 **워커**가 처리한다. 판매자의 요청은 바로 끝나고(202), 화면이 2초마다 결과를 확인한다.

## 3. 영역별로 무엇을, 왜

### 3.1 DB (Flyway 마이그레이션)
| 무엇 | 왜 |
|---|---|
| 테이블은 Flyway가 만들고, Hibernate는 **검사만** 한다(`ddl-auto=validate`) | 엔티티와 테이블이 어긋나면 앱이 시작하지 않는다. 그래서 ERD와 코드가 따로 놀 수 없다 |
| **AI 원본(`raw_result`)과 판매자 확정본(`products`)을 따로 저장** | PoC에서 가장 잘한 설계다. 프롬프트·모델을 바꿨을 때 전후 비교가 가능하다 |
| 판매자가 추가한 "AI가 놓친 상품"도 후보 테이블에 남긴다(`origin=SELLER`) | 카테고리 정확도·정밀도·재현율이 SQL 한 줄로 나온다(2차 회의 지표) |
| DB 로케일이 `C`면 마이그레이션이 **일부러 실패**한다 | `C` 로케일에서는 키릴 문자 검색이 항상 0건이다. 팀원 Windows PC의 "기존 DB"에서 조용히 틀리는 것을 막는다 |
| 목 데이터는 dev 프로필에서만 들어간다(`R__dev_mock_data.sql`) | 운영 DB에 가짜 데이터가 섞이지 않게 하기 위해서다. 여러 번 실행돼도 중복되지 않게 썼다 |

### 3.2 백엔드 구조
| 무엇 | 왜 |
|---|---|
| **기능별 패키지** 안에 Controller → Service → Repository | 4차 회의에서 팀이 공부한 구조 그대로다. 맡은 사람이 한 폴더만 보면 된다 |
| Lombok을 쓰지 않고, DTO는 Java `record`로 썼다 | 팀이 쓰는 JDK 23에서는 Lombok 자동 처리가 기본으로 꺼져 있어 설정 문제가 잦다 |
| 오류 응답에 `code`를 넣는다(`STORE_SLUG_TAKEN` 등 17개) | 화면은 HTTP 상태가 아니라 코드로 분기하고, `detail` 문장은 그대로 보여준다 |
| 판매자 API는 `/seller/**`, 구매자 API는 `/stores`·`/products` | 권한 설정이 경로 단위로 단순해진다. 공개 응답에 판매자 전용 정보가 섞이는 실수도 막는다 |

### 3.3 로그인 (목 로그인)
| 무엇 | 왜 |
|---|---|
| dev에서만 `/dev/login`(사용자 고르기)이 생긴다 | 팀 결정(임시 결정 #1). 로그인 구현에 시간을 쓰지 않고 핵심 기능부터 만들기 위해서다 |
| 목 로그인도 **진짜 JWT**를 발급하고, 나머지 API는 토큰만 본다 | 실증 전에 실제 로그인을 붙일 때 **로그인 API와 로그인 화면만** 바꾸면 된다 |

### 3.4 사진
| 무엇 | 왜 |
|---|---|
| **브라우저에서 먼저 줄여서** 올린다(긴 변 2048px) | 현지 모바일 속도가 143개국 중 139위다(조사 §1). 원본을 그대로 올리면 느리고 5MB 제한에 걸린다 |
| 서버에서 다시 검사한다: 실제 이미지인지, 픽셀 폭탄인지, EXIF 방향 보정, **위치 정보 제거**, 썸네일 생성 | 브라우저를 믿지 않는다. EXIF 제거는 개인정보 때문이다(조사 §8) |
| 저장소를 인터페이스(`ImageStorage`)로 분리 | 지금은 로컬 디스크다. S3로 바꿀 때 구현체만 교체하면 되고 DB는 그대로다 |
| 같은 사람이 같은 파일을 다시 올리면 기존 사진을 돌려준다 | SNS 사진을 한꺼번에 올릴 때 중복이 쌓이지 않는다 |

### 3.5 AI 스캔 (핵심)
| 무엇 | 왜 |
|---|---|
| 요청은 바로 202로 끝나고, **워커가 나중에 처리**한다 | Gemini는 수십 초가 걸릴 수 있다. PoC는 요청 하나가 최대 300초를 기다렸다(2차 회의 결정) |
| 큐는 **PostgreSQL 테이블 하나**다(`FOR UPDATE SKIP LOCKED`) | Redis 같은 별도 메시지 큐를 배울 필요가 없다. 워커를 늘려도 같은 작업을 두 번 처리하지 않는다 |
| 429(한도 초과)·타임아웃은 **30초, 60초 뒤 다시 시도**(최대 3번). 형식 오류는 바로 실패 | 한도 초과 직후 연속으로 호출하면 한도를 더 빨리 소진한다. 다시 해도 안 될 오류는 기다릴 이유가 없다 |
| AI 호출은 **DB 트랜잭션 밖**에서 한다 | 수십 초 동안 DB 연결을 붙잡지 않기 위해서다 |
| 카테고리 목록을 **DB에서 만들어 AI에 보낸다** | PoC는 Python과 Java에 카테고리를 따로 적어 두고 있었다. 이제 DB 한 곳만 고치면 된다 |
| **가짜 AI 모드**(`VISION_MODE=fake`) | 무료 키는 하루 요청 한도가 있다. 화면 개발과 테스트에 한도를 쓰지 않는다. 캡션에 `#fail429`를 넣으면 재시도 화면도 확인할 수 있다 |

### 3.6 검수
| 무엇 | 왜 |
|---|---|
| 검수는 **한 번에 확정**한다(하나의 트랜잭션) | 중간에 실패해도 절반만 저장되는 일이 없다 |
| 모든 AI 후보에 **수락·거절을 강제**한다 | 지표 계산에 "미결정"이 남지 않는다 |
| 캡션에 적힌 가격만 가격 칸에 미리 채운다 | 사진만 보고 AI가 가격을 지어내지 않게 하기 위해서다 |
| 카테고리를 고르면 **판매 단위가 자동으로 바뀐다**(말린 과일 → kg) | 등록 시간을 줄인다(목표 30초) |

### 3.7 상품·재고
| 무엇 | 왜 |
|---|---|
| 수정은 `PUT`(폼 전체)으로, 상태와 재고는 **버튼마다 따로 만든 API**로 처리 | PATCH에서는 "안 보냄"과 "비우기"를 구분하기 어렵다. 재고 `null`은 "관리 안 함"이라는 뜻이라 꼭 구분해야 했다 |
| **재고는 판매자가 직접 관리**하고, 주문 접수 때만 "재고에서 뺄까요?"를 묻는다 | 팀 결정. 매장과 온라인에서 동시에 팔아서 자동 차감하면 실제와 어긋난다. 빼고 나서 주문이 취소되면 되돌린다 |
| 발행하려면 가격이 필수 | "가격은 DM 문의" 문제를 푸는 것이 서비스의 목적이다(조사 §5). 흥정 관행은 "흥정 가능" 표시로 존중한다 |
| AI 검수로 만든 초안은 지우지 않고 **보관**만 한다 | 지우면 지표용 "후보 → 상품" 연결이 끊긴다 |

### 3.8 검색
| 무엇 | 왜 |
|---|---|
| 부분 일치(`ILIKE`)와 유사도 검색(trigram)을 함께 쓴다 | "살구" 같은 두 글자 한글 검색어는 유사도만 쓰면 빠질 수 있었다(ERD 검증에서 0.30) |
| 대분류를 고르면 소분류까지 포함한다 | "식품"을 누르면 말린 과일·견과류가 모두 나와야 한다 |
| 번역이 없으면 기본 언어로 대신 보여준다 | 운영 언어를 바꾼 직후에도 빈 화면이 나오지 않는다 |

### 3.9 주문
| 무엇 | 왜 |
|---|---|
| 한 주문 = 한 상점. 장바구니는 브라우저에만 저장 | 상점마다 판매자가 따로 접수하고 따로 연락한다 |
| 상품명·단가를 주문 시점 값으로 저장(스냅샷) | 상품을 나중에 고쳐도 주문 내역은 바뀌지 않는다 |
| 흥정 상품이 있으면 "예상 금액"으로 표시 | 최종 가격은 대면으로 정해진다 |
| 결제는 현금·송금 기록만 남긴다 | 실결제는 범위 밖이다(2차 회의). 현지는 현금과 지갑 송금이 주류다(조사 §4) |

### 3.10 지표 화면
- 2차 회의 지표(카테고리 정확도 80%, 등록 30초)를 **목표와 함께** 보여준다. 프롬프트 버전으로 걸러서 v2와 v3 같은 전후 비교도 할 수 있다. 주간 보고서에 숫자를 그대로 옮겨 쓰면 된다.

### 3.11 AI 서버 (프롬프트 v3)
PoC와 비교하면 이렇게 바뀌었다. 사진 1장이 **1~3장**(인스타 캐러셀)이 됐고, 출력 언어가 한국어 고정에서 **요청마다 지정**으로 바뀌었다. 카테고리는 코드에 고정돼 있던 것을 **요청으로 받고**, 목록 밖 코드는 스키마에서 거른다. 가격은 항상 비워두던 것에서 **캡션에 적힌 가격만** 채우는 것으로 바뀌었다. 사진 검증과 오류 처리는 PoC에서 검증된 코드를 그대로 썼다.

### 3.12 프런트엔드
| 무엇 | 왜 |
|---|---|
| **휴대폰 화면 기준**으로 만들었다 | 판매자는 시장에서 휴대폰으로 사진을 찍는다 |
| 상점 템플릿 3종(진열대형·가격표형·공방형)을 **같은 데이터로** 그린다 | 템플릿을 바꿔도 서버는 그대로다. 대표 색은 상점마다 적용된다 |
| 스캔 결과는 2초마다 확인하고, 2분이 지나면 "검수 대기함에서 확인"으로 안내한다 | 느린 회선에서 화면을 붙잡아 두지 않는다. 작업은 서버에서 계속된다 |
| 상태·단위 이름을 `format.js` 한 곳에 모았다 | 운영 언어를 바꿀 때 여기부터 번역한다 |
| WhatsApp 문의 버튼 | 현지 메신저 점유율은 IMO·WhatsApp이 압도적이다(조사 §3) |

## 4. 현지 조사가 바꾼 설계

| 조사 내용 | 바뀐 설계 |
|---|---|
| 흥정이 관행이고, 가격 표시가 없는 매대가 많다 | 가격 방식을 정가와 "흥정 가능"으로 나누되, 발행할 때 가격은 필수 |
| 말린 과일·향신료는 무게로 판다 | 판매 단위(kg·m 등)와 소수 수량, 카테고리별 기본 단위 |
| 타직어(키릴)와 러시아어를 쓴다 | 언어별 번역 테이블, AI 출력 언어 지정, UTF-8 로케일 필수 |
| 모바일 인터넷이 느리다 | 브라우저에서 사진 축소, 썸네일, 비동기 스캔 |
| 메신저는 IMO·WhatsApp 중심이다 | 상점 연락처는 WhatsApp 우선, 공개하려면 연락처 필수 |
| 현금과 지갑 송금이 주류다 | 결제는 현금·송금 기록만 |
| 주소에 랜드마크를 함께 쓴다 | 상점·배송 주소에 "랜드마크" 칸 |
| 해외 전송 시 동의가 필요할 수 있다 | 가입 동의 시각 저장, 사진에서 위치 정보 제거 |

## 5. 검증하면서 찾아 고친 버그

| # | 증상 | 원인 | 어떻게 찾았나 |
|---|---|---|---|
| 1 | 카테고리·시장 필터가 무시됨 | JSON은 snake_case로 자동 변환되지만 `?category_id=` 쿼리 파라미터는 변환되지 않음 | 자동 테스트 |
| 2 | 입력 오류 응답에 `code`가 없음 | Spring Boot 기본 오류 처리기가 우리 처리기보다 먼저 가로챔 | 자동 테스트 |
| 3 | 방금 만든 스캔을 큐가 못 볼 수 있음 | PostgreSQL `now()`는 트랜잭션 시작 시각이라서 | 테스트 작성 중 |
| 4 | 판매자가 추가한 상품의 카테고리가 잘못되면 500 오류 | 카테고리 검사보다 저장이 먼저 실행됨 | 코드 검토 |
| 5 | 키릴 문자 검색이 0건 | DB 로케일이 `C`였음 | ERD 검증 |
| 6 | 목 데이터의 상품 이름이 엉뚱한 상품에 붙을 수 있음 | 입력 순서에 기대는 매핑 | ERD 검증 |
| 7 | 판매자 화면에서 로그아웃하면 다시 로그인 화면으로 감 | 로그인 필요 검사가 홈 이동보다 먼저 실행됨 | 브라우저 확인 |
| 8 | 휴대폰에서 장바구니 상품명이 한 글자씩 세로로 쪼개짐 | 수량 입력이 한 줄을 다 차지함 | 브라우저 확인(휴대폰 크기) |

## 6. 임시로 둔 것 (실증 전에 바꿀 것)
