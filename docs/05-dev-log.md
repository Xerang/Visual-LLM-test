## 작업 기록

### 1. CI (2026-10-12)
- 무엇: `.github/workflows/ci.yml`. PR과 main 푸시마다 backend `mvn test`(PostgreSQL 16 서비스), vision `unittest`, frontend `npm ci && npm run build`.
- 정정(같은 날): 처음 올린 버전은 **실행되지 않았다.** 프로젝트가 저장소 최상위가 아니라 `bozor-photo-scan-gemini-updated/` 폴더 안에 있었는데, GitHub는 최상위의 `.github/workflows`만 읽기 때문이다(PR 템플릿·README 표시도 같은 이유로 안 됐다). 프로젝트 전체를 `git mv`로 저장소 최상위로 옮겨 고쳤다(경로 외 변경 없음, 이동 후 백엔드 44·AI 서버 16 테스트와 프런트 빌드 통과).
- 검증: 최상위 이동 커밋(`52b9911`)의 PR #2 실행에서 backend·vision·frontend 3개 작업 모두 통과(GitHub Actions). 이후 커밋도 PR마다 자동 실행된다.

### 2. 모델 비교 도구 (2026-10-12)
- 무엇: `vision/tools/evaluate.py`. 정답셋(사진별 정답 소분류 코드)으로 모델별 정밀도·재현율·완전 일치(소분류·대분류)와 응답 시간 중앙값을 계산한다.
- 정확성: `/v1/scan`과 같은 함수(`scan_images`)를 쓰도록 AI 서버 코드를 분리했다(동작 변화 없음, 기존 테스트 통과). 채점은 카테고리 다중집합 일치로 정의하고, 손으로 계산한 값과 비교하는 테스트를 넣었다.
- 무료 한도 보호: 성공 결과 캐시, 429 즉시 중단·이어 하기, `--max-calls`·`--sleep`.
- 검증: 테스트 9개 추가(AI 서버 테스트 16개 통과). 실제 Gemini로 1장 평가(머그잔·사과 → 정답 2개 모두 일치, 44.4초).
- 한계: 상품명·설명의 질과 캡션 가격 추출은 채점하지 않는다. 서비스는 Java에서 한 번 줄인 사진을 다시 정규화하지만, 도구는 Python 정규화만 한다(둘 다 긴 변 2048px JPEG).

### 버그 수정: Gemini 과부하가 "바로 실패"로 처리되던 문제 (2026-10-12)
- 발견: 위 실제 평가에서 Gemini가 `503 high demand`를 반환했다. AI 서버가 이를 502로 바꿔 Spring 워커가 **재시도 없이 실패** 처리하는 구조였다. 서비스였다면 Gemini가 잠깐 바쁘기만 해도 판매자가 "분석 실패"를 봤다.
- 수정: Gemini 500·503 → AI 서버 503 → Spring `AI_UNAVAILABLE`(재시도). 400·401·403·404·형식 오류는 그대로 502(바로 실패).
- 검증: AI 서버 테스트 2개, Spring `HttpVisionClientTest` 8개(상태 → 오류 코드·재시도 여부 전체 표) 추가. API 명세 5.5·7장 갱신.

### 3. 사진 접근 제어 (2026-10-12)
- 근거: 임시 결정 #9("검수 전 사진은 주인만, 공개 상품 사진만 공개"). 사진 id가 1, 2, 3… 순번이라 주소의 숫자만 바꾸면 다른 판매자가 아직 공개하지 않은 스캔 사진·초안 사진을 볼 수 있었다.
- 무엇:
  - 공개 사진 = 판매 중(`PUBLISHED`) 상품이 공개(`ACTIVE`) 상점에 있거나 공개 상점의 로고·배너. 서명 없는 주소로 누구나 본다(구매자 화면은 변경 없음).
  - 그 밖의 사진은 주인에게 준 응답(업로드 결과, 판매자 상품·스캔 작업·상점 응답)에 담긴 **서명 주소**로만 본다. 맞지 않으면 404.
  - 서명 = HMAC-SHA256(`"image:{id}:{exp}"`), 만료는 1시간 단위로 맞춤(폴링 중 주소가 안 바뀌어 캐시 유지). 서명 키는 JWT 키를 함께 쓰지만, JWT 서명 입력(base64url 문자열)에는 `:`가 없어 두 서명이 서로 바꿔 쓰일 수 없다.
- 왜 토큰 검사가 아닌 서명 주소인가: 화면의 `<img>`는 로그인 토큰 헤더를 보낼 수 없다. 쿠키 로그인으로 바꾸는 것은 임시 결정 #1(로그인 방식)과 엮여 있어 손대지 않았다. S3로 바꿀 때(#6)도 같은 서명 URL 방식이라 화면은 그대로다.
- 검증: `ImageAccessTest` 4개(업로드 사진은 서명 주소만 200·일반 주소 404 / 다른 사진에 서명 재사용·서명 변조·만료 연장 404 / 초안 404 → 판매 중 200(public 캐시) → 숨김 404, 판매자 서명 주소는 200 / 공개 상점 로고 200 → 상점 숨김 후 404), `ImageUrlSignerTest` 3개(만료 정렬, 만료 경계, 다른 키·다른 사진). 백엔드 전체 51개 통과. 브라우저(모바일 폭)에서 판매자 상품·AI 스캔 탭은 서명 주소, 공개 상점은 일반 주소로 사진이 깨짐 없이 표시됨.
- 한계: 로그아웃해도 이미 받은 서명 주소는 최대 2시간 유효하다. 상품을 숨기기 전에 받아 간 공개 사진은 브라우저·중간 캐시에 최대 하루 남을 수 있다. 장바구니에 담아 둔 상품이 숨겨지면 장바구니 썸네일이 안 보인다(그 상품은 주문도 막히므로 영향 작음).

### 4. SNS 사진 일괄 등록 + 상점 온보딩 소요시간 (2026-10-12)
- 근거(2차 회의 원문): 추가 기능 "기존 SNS 이미지 일괄 등록", "시연 시점에 상품이 비어 있는 문제에 대해서는 판매자가 보유한 기존 SNS 이미지를 직접 일괄 업로드하는 방식으로 대응", 검증 지표 "상점 온보딩 소요시간 — 이미지 20장 기준 5분 이내". 범위 조정 "상품 사진 1~3장".
- 무엇:
  - 화면: 상점 관리 → "SNS 사진 한꺼번에 등록". 여러 장을 고르면 사진 한 장 = 게시물 하나로 시작하고, 캐러셀은 "앞 게시물과 합치기"(최대 3장), 게시물마다 캡션(가격이 있으면 AI가 가격 칸에 채움). 분석 요청 후 진행 화면에서 끝난 게시물부터 차례로 검수("다음 게시물 검수하기").
  - API 3개(명세 39~41), 테이블 `import_batches` + `scan_jobs.import_batch_id`(V3). AI 처리·검수는 단건 스캔을 그대로 쓴다.
  - 게시물 최대 20개: 지표 기준(20장)과 무료 키 한도(임시 결정 #7). 한 묶음 = Gemini 호출 최대 20번.
- 지표 정의(서버 시각만 사용): 온보딩 소요시간 = 묶음 시작(사진을 고른 직후, **업로드 전**) → 모든 게시물 검수 완료. 실패한 게시물이 남으면 완료가 아니다. 사진 업로드·캡션 입력 시간(`prepare_seconds`)을 따로 보여준다. 사진 수가 다른 묶음은 20장으로 환산하지 않고 묶음별 사진 수를 함께 낸다.
- 함께 바꾼 것(각각 근거):
  - **단건 스캔 우선 처리**: 워커는 한 번에 하나씩 처리한다. 일괄 등록 20건 뒤에 다른 판매자의 단건 스캔이 줄 서면 "1건 30초" 지표가 깨진다 → 큐에서 단건을 먼저 꺼낸다.
  - **등록 소요시간 지표는 단건만**: 일괄 등록 게시물은 대기 시간이 섞여서 단건 지표를 왜곡한다 → 단건만 세고, 일괄 등록은 온보딩 지표로 잰다.
  - **"상품 없음" 검수**: AI 후보가 0개면 빈 `items`로 검수를 끝낼 수 있다. SNS에는 가게 전경 같은 사진도 섞여 있어서, 이것을 끝낼 수 없으면 묶음이 영원히 완료되지 않는다. 후보가 있으면 여전히 모두 결정해야 한다.
  - 가짜 AI에 `#empty`(후보 0개) 추가 — 위 흐름을 Gemini 없이 확인·시연하기 위해(임시 결정 #12).
- 검증: `ImportBatchTest` 6개(게시물별 SNS_IMPORT 작업 생성·빈 캡션 null·한 번만 요청, 게시물 간 같은 사진·21개 거절, 다른 판매자 403, 단건 우선 처리, 모두 검수하면 완료·온보딩 지표 집계·단건 지표에서 제외, 후보가 있으면 빈 검수 거절). 백엔드 57개 통과, 프런트 빌드 통과. 브라우저(모바일 폭, 가짜 AI): 사진 4장 → 게시물 3개(1장·2장 합침·1장 `#empty`) → 분석 → 차례로 검수(수락 1, 모두 거절, 상품 없음) → 진행 화면 "걸린 시간 1분 22초" → 관리자 지표에 묶음 #1(사진 4장, 게시물 3, 발행 1, 82초·준비 26초) 표시. 문서의 SQL을 dev DB에서 실행해 같은 값(82초) 확인.
- **팀 확인 필요**: (1) 온보딩 시작점을 "사진을 고른 순간"으로 잡았다. 상점 정보 입력 시간까지 넣을지 정해야 한다. (2) 20장 실측은 실제 Gemini로 해야 의미가 있다. 워커가 하나씩 처리하므로 AI 시간만 실측 1건 10.8초 기준 20건 약 3.6분(추정)이고, 검수는 끝난 것부터 동시에 진행된다. 무료 키 한도(#7) 안에서 하루 한 번 정도만 잴 수 있다.
- 한계: 고른 사진을 게시물에서 빼도 업로드된 사진 파일은 남는다(어디에도 공개되지 않음, #9). 일괄 등록 목록 화면은 따로 없고, AI 스캔 탭에 "일괄 #N" 표시와 검수 화면의 링크로 돌아간다.

### 5. 배포 준비: 서버 하나로 API + 화면 (2026-10-12)
- 근거: 2차 일정 "11~12주 추가 기능 및 배포", 시스템 구성 "React – Spring Boot – FastAPI – PostgreSQL". 느린 회선(조사 §1).
- 정정: 작업 목록의 근거를 처음에 "일정 10주차 배포"로 적었다. 2차 회의 원문을 다시 확인해 보니 10주차는 "통합 데모 1차", 배포는 "11~12주"다. 고쳐 적었다.
- 무엇:
  - `mvn clean package -Pwith-frontend`: 빌드한 화면(`frontend/dist`)을 jar 안 `static/`에 넣는다. 화면을 빌드하지 않았으면 안내 문구와 함께 빌드가 멈춘다.
  - `FrontendResourceConfig`: 화면 주소로 바로 들어오거나 새로고침해도 `index.html`, 없는 API·파일은 404. `assets/`(해시 이름) 1년 캐시, `index.html`은 no-cache.
  - gzip 압축 켬(`server.compression.enabled`). 보안 설정: `/api/` 밖의 GET(화면 파일·화면 주소)은 로그인 없이 허용, API 권한은 그대로.
  - CI에 `package` 작업 추가(jar 안에 `static/index.html`이 있는지 검사).
  - README §8 배포 절차·주의(목 로그인 상태라 공개 상시 운영 금지, `JWT_SECRET` 직접 설정), 실증 전 체크리스트에 한 줄 추가.
