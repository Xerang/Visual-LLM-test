# 협업 규칙

3명이 14주 동안 지킬 수 있는 만큼만 정했다. 바꾸고 싶으면 이 문서를 고치는 PR을 올린다.

## 브랜치

```
main ─────●──────────●──────────●───── 언제든 시연할 수 있는 상태
           \        /  \        /
 feat/scan-review ─●    fix/cart-layout
```

- `main`: **언제든 시연할 수 있는 상태.** 직접 push 하지 않고 PR로만 합친다.
- 작업 브랜치: 작업 하나에 브랜치 하나. 이름은 `feat/…`(기능), `fix/…`(버그), `docs/…`(문서), `chore/…`(설정·정리).
- 며칠 안에 합칠 수 있는 크기로 쪼갠다. 오래 열어 둔 브랜치일수록 충돌이 커진다.
- 시연 시점은 태그로 남긴다: `demo-1`(10주차 통합 데모), `final`(최종 발표).

> 2차 회의에서는 main / develop / feature 구조로 정했지만, 3인 팀에서는 main과 develop을 맞추는 비용이 커서 develop 없이 운영한다.

## PR

- **팀원 1명이 승인하고 테스트가 통과해야** 합친다. 합칠 때는 Squash merge.
- PR 설명은 템플릿(`.github/pull_request_template.md`)을 채운다.
- API나 DB를 바꾸면 **같은 PR에서 문서도 고친다**: `docs/03-api.md`, `docs/02-erd.md`.
- 임시 설정(목 로그인, 한국어 운영 등)을 바꾸면 `docs/00-temporary-decisions.md`를 갱신한다.

## 꼭 지킬 것

1. **키·비밀번호는 커밋하지 않는다.** `vision/.env`는 `.gitignore`에 있다. 리뷰할 때도 한 번 더 본다.
2. **이미 main에 들어간 DB 마이그레이션 파일은 고치지 않는다.** 바꿀 내용은 새 버전 파일(`V3__…`)로 추가한다.
3. **마이그레이션 번호 충돌**: 두 브랜치가 같은 번호(`V3__`)를 만들 수 있다. 합치기 직전에 main을 받아 번호를 다시 확인한다.
4. **테스트를 돌리고 올린다.**

```bash
cd backend && mvn test
cd vision && .venv/bin/python -m unittest discover -s tests
cd frontend && npm run build
```
